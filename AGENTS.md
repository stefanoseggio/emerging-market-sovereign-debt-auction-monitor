# AGENTS.md - Emerging-Market Sovereign Debt Auction Monitor

Technical notes for whoever (human or AI) touches this actor next. Authored 2026-09-16, applying
the fleet reference architecture established in Actor #1 (TED) and Actor #2 (UK Modern Slavery
Registry) to a third, genuinely different real data-access mechanism. Every claim below was
verified against the live source, not assumed from the mandate's framing.

## 0. The real data source — verified live, not the mandate's generic framing

The mandate named no specific target ("e.g., LatAm/MENA sovereign issuance calendars, treasury
auction feeds, or central bank announcement portals"). This session's own earlier
`global_actor_expansion_and_market_intelligence_report.md` had already identified emerging-market
sovereign debt monitoring as a real, wide-open Apify Store niche (OECD/S&P-cited market of
$3T+/year EMDE borrowing) — this build picks a concrete, live, verifiable primary source rather
than a placeholder concept.

**Real target confirmed**: Brazil's National Treasury (Secretaria do Tesouro Nacional), via the
official **Tesouro Transparente** open-data portal (`tesourotransparente.gov.br`), which runs on
**CKAN** (the same standardized open-data platform used by data.gov, data.gov.uk, etc. — a real,
documented REST API, not a bespoke one). Dataset `ds013`, *"Resultado dos leilões da Dívida
Pública Mobiliária Federal Interna"* (Results of Federal Domestic Public Securities Debt
auctions), confirmed live via:

```
GET https://www.tesourotransparente.gov.br/ckan/api/3/action/package_show?id=ds013
```

This returns real per-**registry-year** file resources (2000–2026, confirmed present up to and
including 2026, with 2026's file containing real auction results through **2026-09-15** — one day
before this actor's build date, confirming the source is actively, currently maintained, not
stale):

```
https://sisweb.tesouro.gov.br/apex/cosis/rleiloes/arquivos/unico/desc/historico-leiloes-{YEAR}.xlsx
```

Licensed under the **Open Data Commons Open Database License (ODbL)**, per the dataset's own
real license metadata. No authentication required.

### Why the per-year file, not the "todos" (all-years) file

A combined `historico-leiloes-todos.xls` resource also exists (one worksheet per year in a single
workbook), but the per-year files are simpler to fetch/cache/diff independently (mirrors Actor
#2's per-year CSV pattern) and avoid re-downloading 26 years of history to check whether only the
current year changed.

## 1. A real transport limitation, found live — and the honest design response

Unlike Actor #2's UK registry (which supports `HEAD` requests with a real `Content-MD5` header),
this server — an Oracle APEX application (`sisweb.tesouro.gov.br/apex/...`) fronted by IIS —
**returns HTTP 405 (Method Not Allowed) for both `HEAD` and `Range` requests**, confirmed live by
direct testing. There is no way to cheaply check "has this year's file changed" without
downloading it.

**This is not treated as a blocker, because it doesn't need to be one**: a full year's file is
small (58–85 KB observed live for 2024–2026), so the actual cost of always downloading it is
negligible bandwidth and well under a second, unlike TED's paginated queries or the UK registry's
8–15 MB CSVs.

**A second real finding, corrected mid-build**: the first version of this actor planned to compare
this server's `ETag` response header against a cached value to at least skip the CPU cost of
parsing/diffing an unchanged year, mirroring Actor #2's `Content-MD5` pattern. Direct live testing
disproved this before it shipped: **three consecutive `GET` requests for the exact same,
byte-identical 2026 file returned three different `ETag` values.** This is not a real content
signal — it appears to be a per-response value generated by this Oracle APEX application, not a
content hash. Building a cache keyed on it would have looked like an optimization while never
actually hitting, which is worse than not having one (a false claim of efficiency, not just a
missing one). **This actor therefore always downloads and fully parses every selected year, every
run** — there is no file-level "unchanged, skip" fast path here at all, unlike Actors #1 and #2.
The zero-cost guarantee this fleet is built on still holds, just at a different layer: the
per-record SHA-256 content fingerprint (§5) is what prevents an unchanged auction from being
re-pushed or re-billed — the "zero-cost" property is per-record here, not per-file.

real Portuguese header row, row index 6 is the real English header row, and data starts at row

internal field names (both header rows were read live, not assumed to exist from a single-row

**Real, confirmed bond types** (live-observed in 2024/2026 data): `LTN` (zero-coupon, fixed

coupon), `NTN-F` (fixed rate, semi-annual coupon). **Real, confirmed auction types** (from the

## 3. Three mandate assumptions corrected against this real source

### No ISIN/CUSIP

The mandate asked to track "ISIN, CUSIP, local codes." **This real source publishes none of the
first two.** Brazilian domestic Treasury securities (LTN/LFT/NTN-B/NTN-F) settle through Brazil's
own SELIC system and are identified operationally by **bond type + maturity date**, not by
ISIN/CUSIP — there is no international security identifier in this dataset to extract, and
inventing one would be fabrication. This actor's real local instrument identifier — used by
`benchmarkRateKey()` in `src/deltaEngine.ts` for rate-history tracking (§5.4) — is
`{bondType}::{auctionType}::{maturityDate ISO date}` (e.g. `LTN::Venda::2025-04-01`), which is
what the source itself effectively uses to distinguish one outstanding security's price
discovery from another across auction dates. (The full per-auction-event `recordId`, a distinct,
five-component key, is documented separately in §5.1.)

### No true bid-to-cover ratio

The mandate asked for "bid-to-cover ratios." **This source does not publish total market demand**
(the sum of all bids submitted, accepted or not) — only `quantityOffered` (the Treasury's own
supply-side target) and `quantityAccepted` (what was actually placed). A genuine bid-to-cover
ratio requires the former; this actor computes and exposes a real, different, honestly-labeled
metric instead: **`coverageRatio = quantityAccepted / quantityOffered`** (a take-up/coverage
ratio — how much of the offered supply was actually placed), explicitly documented as NOT a
bid-to-cover ratio in the dataset schema and README, rather than silently relabeling it as one.

### No structured forward-looking auction calendar

The mandate's event model named `CALENDAR_MUTATED` as a distinct structural-change type,
implying a full announcement → bidding → settlement lifecycle. A real quarterly
"DOMESTIC PUBLIC DEBT AUCTIONS CALENDAR" communiqué does exist (confirmed live via search,
published as PDF at `thot-arquivos.tesouro.gov.br/comunicado/*`), but **it is a PDF press
release, not a structured feed** — reliably parsing tabular data out of a government PDF would be
a fundamentally less reliable extraction method than this actor's verified XLSX pipeline, and
mixing a fragile PDF-scraping path into a "zero-defect, financial-grade" actor would undermine the
actual reliability guarantee this fleet is built on. **`CALENDAR_MUTATED` is not implemented.**
Instead, this actor uses the same real 4-state model as Actors #1/#2, correctly grounded in what
this source actually and reliably supports: `NEW_AUCTION` (a specific auction/round observed for
the first time), `AUCTION_RESULT_REVISED` (an already-seen auction's published figures changed —
a real, plausible occurrence for government data, e.g. a correction), `AUCTION_UNCHANGED`, and
`BASELINE_SNAPSHOT`. Because results are published within about a day of the real auction (the
2026 file's most recent row is dated one day before this actor's build), `NEW_AUCTION` still
functions as a near-real-time "something happened" signal, just anchored to result publication
rather than a pre-auction announcement.

## 4. Financial-grade numeric and date canonicalization

### Excel date serials — a real timezone hazard, found and worked around

`xlsx`'s `cellDates: true` option converts Excel's date serials to JS `Date` objects, but live
testing during this build showed **timezone-sensitive behavior**: a serial expected to represent
UTC midnight for a given calendar date came back as `...T03:00:00.000Z` in this build
environment, not `...T00:00:00.000Z`. For a "financial-grade, ISO-8601 UTC" requirement, silently
trusting a library conversion that varies with the host's local timezone is not acceptable. This
actor reads the **raw numeric serial** (not `cellDates`) and performs its own explicit,
timezone-independent conversion in `src/dataSource.ts` (`excelSerialToIsoDate`): Excel's epoch is
1899-12-30 in UTC, so `isoDate = new Date(Date.UTC(1899, 11, 30) + serial * 86_400_000)`, formatted
as a plain `YYYY-MM-DD` date (these are calendar dates with no time-of-day component in the
source, so no time or timezone offset is fabricated onto them).

**A second real bug in this same area, found by adversarial review**: an earlier version defaulted
an unparseable-but-non-empty auction-date cell (`auctionDateSerial`) to serial `0` via `?? 0`
rather than propagating `null`. `excelSerialToIsoDate(0)` computes a real-looking but entirely
fabricated date, `1899-12-30` — exactly the kind of invented data this fleet's "never fabricate"
discipline exists to prevent. `auctionDateSerial` is now nullable end-to-end
(`RawAuctionRow`/`toNumberOrNull`, no `?? 0` fallback), and `normalizeAuction()` throws and
rejects the row if it's null, the same way it already rejected a row with a missing `bondType`.

### Rate precision — basis points as the canonical integer form

Rates arrive as raw decimal fractions (e.g. `0.098997` for 9.8997%). Floating-point decimal
fractions are the wrong representation for "financial-grade precision" threshold comparisons
(repeated float arithmetic on fractions like this accumulates real, non-obvious rounding error).
This actor converts every rate to an **integer number of basis points, rounded to the nearest
whole bp**, and treats basis points — not the raw fraction — as the canonical unit for storage,
hashing, and threshold comparisons. The original decimal fraction is still preserved in the output
record for transparency, but every internal comparison (change detection, threshold breach)
operates on the integer bp value.

A plain `Math.round(rate * 10_000)` has two real, adversarial-review-caught defects, both fixed in
`src/quantEngine.ts`'s `toBasisPoints()`: `Math.round` breaks exact half-bp ties toward +Infinity,
not away from zero, so it is sign-asymmetric (`0.09895` → 990 bps, but `-0.09895` → -989 bps, not
-990) — not realistically reachable via this actor's actual data (Brazilian nominal Treasury
yields are always positive), but wrong for a function this document itself calls
precision-critical; and IEEE-754 multiplication noise can push a mathematical half-bp tie just
under the rounding boundary (`0.00015 * 10_000` evaluates to `1.4999999999999998`, not `1.5`,
rounding to 1 bp instead of 2). Both are fixed with an intermediate `toFixed(4)` pass (absorbing
the floating-point noise to a precision far finer than any real published rate) followed by a
sign-symmetric round (`Math.sign(x) * Math.round(Math.abs(x))`).

### Currency

100% of this source's data is BRL-denominated (`Financeiro (R$)`). The schema carries an explicit
`currency` field (fixed to `"BRL"` for this actor, not fabricated as multi-currency support this
source doesn't have) so the type is genuinely extensible if a future actor adds a
different-currency source, without claiming multi-currency coverage that doesn't exist today.

## 5. Delta engine

- **Unique record key**: `{bondType}-{auctionType}-{maturityISODate}-{auctionISODate}-{round}` —
  five components, all required. This is a real correction made mid-build: a first version
  omitted `auctionType`, and live testing against the real 2026 file caught the exact resulting
  collision - a 2026-03-16 LTN row runs a genuine "Extra Compra" (extraordinary purchase) and a
  separate "Extra Venda" (extraordinary sale) for the same bond, maturity, date, and round: two
  real, independent operations, not a duplicate. Without `auctionType`, the second row silently
  overwrote the first's tracked fingerprint and was misclassified as a revision of it - caught
  because a from-scratch baseline run showed 22 unexplained `AUCTION_RESULT_REVISED` events where
  there should have been none, which is what triggered this investigation. The corrected 5-field
  key was verified against 2,850 real rows spanning 2024, 2025, and 2026 with zero collisions.
- **Content fingerprint**: SHA-256 over the canonicalized normalized record (recursive key-sort,
  same discipline as Actors #1/#2), excluding only the single **derived** `recordId` field itself
  (see `hashableFields()` in `src/deltaEngine.ts`) — corrected by adversarial review from an
  earlier, inaccurate version of this doc that claimed all five key-*forming* fields (bondType,
  auctionType, maturityDate, auctionDate, round) were excluded. They are not: those five fields
  remain in the hashed structure alongside the rates/quantities/amounts, so a normalization change
  to any of them (e.g. how `round` strings are formatted) would also change every
  `content_fingerprint`. Same fleet-wide SHA-256-over-BLAKE3 decision as Actor #1 — this actor's
  files are smaller still (58-85 KB) than either prior actor's, so the same "network/IO-bound, not
  hash-bound" reasoning applies with even more headroom.
- **Quantitative threshold layer** (`src/quantEngine.ts`, new to this actor — see below): computed
  independently of, and in addition to, the structural content fingerprint. A structural change
  (any field differs) is necessary but not sufficient to classify as high-value; a threshold
  breach on `acceptedRate` (basis points moved beyond a configured limit versus the same
  `bondType`+`auctionType`+`maturityDate` instrument's last observed value — see
  `benchmarkRateKey()`, §3's "No ISIN/CUSIP" section) or `coverageRatio` (fell below a configured
  floor)
  is what actually drives alerting, mirroring Actors #1/#2's "status fingerprint" pattern but
  extended to real numeric comparisons instead of boolean field changes.

  `benchmarkRateKey()` itself needed the same `auctionType` correction as `buildRecordId()`
  (§5.1), found by adversarial review rather than live testing this time: without it, a
  "Compra"/"Extra Compra" (purchase/buyback) and a "Venda"/"Extra Venda" (sale) operation on the
  same bond+maturity shared one rolling "last observed rate" slot, even though the two are
  economically different price-discovery mechanisms — a buyback rate reflects the Treasury's own
  repurchase offer, not the market's issuance rate. Mixing them produced a spurious
  `rateChangeBps` and could trigger a false threshold-breach alert. This bug shipped in the first
  version despite `buildRecordId()` already having been fixed for the identical root cause,
  because the fix was applied to one function and not searched for elsewhere in the codebase —
  the concrete lesson: fixing a bug class in one place doesn't fix every place that class
  reappears, and adversarial review exists precisely to catch that gap.

## 6. Why property-based testing is genuinely appropriate here (not just requested)

Rate-to-basis-point rounding, Excel-serial-to-date conversion, and coverage-ratio computation are
all pure numeric functions with a large, well-defined input domain (any real rate between 0 and 1;
any positive integer serial; any two positive quantities) — exactly the case property-based
testing is suited for, rather than a handful of hand-picked examples. This actor uses `fast-check`
(the standard TypeScript/JavaScript property-based testing library, integrating directly with
Vitest) for `test/quantEngine.test.ts`'s numeric-precision tests, not renamed unit tests.

## 7. HTTP transport: `impit`, not the native `fetch`

`src/dataSource.ts` makes its one real request (the per-year XLSX download) via a module-level
`Impit` instance (`new Impit({ browser: 'chrome' })`, from the `impit` package), not the global
`fetch`. This gives that request a real, internally-consistent Chrome TLS/HTTP2 fingerprint
instead of Node's native (and distinctively bot-shaped) one — added 2026-09-19 as a fleet-wide
TLS-fingerprint-hardening pilot (Node's own `fetch` is not itself deprecated; this is proactive
hardening, not a bug fix). `src/notifier.ts`'s webhook POSTs (Slack/Teams/user-supplied
`webhookUrl`) deliberately still use the native `fetch` — those calls go to the caller's own
integration endpoints, not a scraped source, so a browser TLS fingerprint buys nothing there.

Two things to know if you touch this again:

- **`Impit.fetch()` is a native binding, not built on the global `fetch`.**
  `vi.stubGlobal('fetch', ...)` does NOT intercept it — it silently does nothing and the real
  network call goes out. `test/dataSource.test.ts` originally mocked global `fetch` this way (12
  call sites); every one of those tests would have started hitting the live Tesouro Transparente
  file server had this not been caught before merge. Fixed by mocking the `impit` module itself
  instead (`vi.mock('impit', ...)`, with `vi.hoisted()` for the mock function reference, and a real
  `function` — not an arrow function — as the mock's `Impit` implementation, since `new Impit(...)`
  requires a constructible mock). Keep that pattern if this file's tests are extended.
- **`vi.restoreAllMocks()` does not reliably clear a plain `vi.fn()` created via `vi.hoisted()`** —
  it only reliably restores real `vi.spyOn()` spies. Without an explicit `fetchMock.mockReset()` in
  `afterEach`, `fetchMock.mock.calls` leaked across tests within the same file (observed live: a
  test asserting 2 calls saw 8, then 12, then 14 — call counts accumulating test-to-test), which
  would have made every `toHaveBeenCalledTimes(...)` assertion in this suite meaningless. This is a
  real gotcha beyond the one already documented in `florida-tenders-monitor/AGENTS.md` for the same
  migration — check for it if you extend this pattern elsewhere in this fleet.
- This file has no `init: RequestInit` parameter and no `: Response`-typed signature anywhere, so
  neither of `impit`'s other two common migration gotchas (the narrower `HttpMethod` union on
  `RequestInit.method`, and `ImpitResponse` not being structurally assignable to the DOM `Response`)
  applied here.

**Site-specific finding**: live-tested directly against the real
`sisweb.tesouro.gov.br` file server on 2026-09-19 (native `fetch()` and `impit.fetch({browser:
'chrome'})` run concurrently against the same 2026 file) — both returned `200 OK` with
byte-identical content (59,433 bytes) and comparable latency. Unlike `diario-oficial-cl-monitor`
(where this same `impit` swap got the Chrome fingerprint actively blocked by that site's WAF), this
Oracle-APEX/IIS-fronted government server shows no fingerprint-based discrimination. `fetchYearAuctions('2026')`
was also re-run end-to-end against the live site through `impit` after the swap and correctly
parsed all 728 real rows.
